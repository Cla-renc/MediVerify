# MediVerify 🛡️

**Counterfeit & Expired Medicine Verification System with Cloned-Code Detection**  
_Built for the Kenyan pharmaceutical context — Pharmacy & Poisons Board (PPB) compliant_

[![CI](https://github.com/your-org/mediverify/actions/workflows/ci.yml/badge.svg)](https://github.com/your-org/mediverify/actions)

---

## 🎯 What is MediVerify?

MediVerify is a full-stack system that lets:
- **Customers** instantly verify any medicine by scanning a QR code or sending an SMS/USSD
- **Manufacturers** register products, generate HMAC-signed QR codes, and manage recalls
- **Pharmacists** track inventory with expiry alerts and recall notifications  
- **Regulators** review clone alerts, manage fake-product heat maps, and configure detection thresholds

**Main technical contribution:** A tri-factor **cloned-code detection engine** using frequency analysis, Haversine velocity checking, and IP entropy scoring.

## 📱 Features

### A. Batch Registration & QR Generation
- HMAC-SHA256 signed unit codes — unforgeable without the server secret
- Export printable QR sheet (PDF) and unit code list (CSV) per batch

### B. Medicine Verification
- Camera QR scanner (in browser via `html5-qrcode`)
- Manual code entry  
- 5 result states: **GENUINE** · **EXPIRED** · **RECALLED** · **SUSPECTED CLONE** · **INVALID**
- Bilingual responses (English + Swahili)

### C. Cloned-Code Detection Engine ⭐
Three independent rules combined into a 0–100 risk score:

| Rule | Trigger |
|------|---------|
| **Frequency** | Code scanned > threshold times |
| **Velocity** | Same code from locations > 800 km/h apart (Haversine formula) |
| **IP Entropy** | > N distinct IP addresses in a rolling window |

Admin can `CONFIRM` (activates clone flag on all future scans) or `DISMISS` each alert.

The rule engine remains the fallback if no model is trained. An optional Isolation Forest adds an anomaly score from scan history, channel mix, device/IP/location spread, travel speed, code age, and batch-relative scan rate. The default final score is 60% rules and 40% ML. Regulators can review the model version, training date, training sample count, and retrain it from the Admin dashboard.

### D. Pack OCR
- Pharmacists can take or upload a pack photo from **Add Stock**.
- OCR extracts the batch number and manufacturing/expiry dates; the values remain editable.
- The pharmacist must confirm the fields before adding inventory. The app checks the batch against the MediVerify registry and warns when it is not found.
- Images are validated, limited to 5 MB, re-encoded without metadata, processed locally, and not saved by the OCR endpoint.
- Windows: install Tesseract OCR and add its folder to `PATH` or set `TESSERACT_CMD`. Linux: `sudo apt-get install tesseract-ocr`. Docker installs Tesseract in the backend image.

### E. English and Swahili Medicine Information Chat
- After a **GENUINE** verification, customers can ask about uses, usual leaflet directions, side effects, warnings, storage, and when to seek care.
- Answers are grounded in the matching `MedicineInfo` record. With no configured LLM key, the app returns the requested record section directly and works offline.
- Seeded medicine entries are marked **SAMPLE - must be reviewed by a pharmacist**. They are demonstration content, not approved clinical references. The Beta-Flagyl/Metronidazole demo product has a matching entry so its registered side-effect information is available to chat.
- Emergency symptoms trigger an urgent seek-care message; the chatbot does not diagnose or provide personalized treatment changes.
- SMS supports `INFO <code>` and `INFO <code> SW`.

### F. Pharmacy Inventory
- Add stock by batch number or unit QR code
- Dashboard shows: near-expiry (30/60/90 days), expired, recalled, low-stock items
- In-app + email/SMS simulation alerts

### G. Suspicious Reports & Heat Map
- Public photo + description reports
- Leaflet/OpenStreetMap heat map for regulators (filters by date, product, county)

### H. SMS & USSD (Africa's Talking)
- USSD callback: menu-based verify/report flow; text responses are returned to Africa's Talking.
- SMS callback: verifies a code or handles `INFO <code>`; with live delivery enabled, replies are sent through the Africa's Talking SMS API.
- **Built-in simulator page** at `/simulator` remains local and does not send real SMS or require a SIM.
- Live delivery is disabled by default and requires an Africa's Talking account, provisioned SMS sender/USSD service code, credentials, and publicly reachable HTTPS callback URLs. Setup instructions are below.

### I. Pharmacy Trust Rating
- **TRUSTED** ≥ 80% · **WATCH** 50–79% · **FLAGGED** < 50%
- Score based on: recalled items in stock, expired items, fake reports linked

### J. Languages
- English & Swahili for all customer-facing pages and SMS/USSD responses

### K. Public dashboard, sign-up & receipts
- `/stats` shows aggregate public scan and registry counts and refreshes every 30 seconds; it does not expose scan locations or personal information.
- Public customers can register and sign in. Manufacturer and pharmacist registrations collect organization/license details and remain inactive until a regulator verifies and activates the account in Django Admin.
- Each recorded verification result can be downloaded as a PDF receipt using its unguessable scan reference.
- Pharmacist pack OCR is already available in the **Add Stock** tab. It requires review and confirmation before stock is submitted.

### L. Regulator live alerts
- The regulator dashboard receives new clone alerts over an authenticated WebSocket and reconnects when the connection drops.
- The default channel layer is in-memory and intended for this single-instance demo deployment. It does not retain notifications while the service is stopped.

## 🔐 Security

| Threat | Mitigation |
|--------|-----------|
| Code guessing | HMAC-SHA256 signatures — 2^96 search space |
| Code cloning | Rule-based frequency/velocity/IP detection combined with optional Isolation Forest |
| Replay attacks | Scan logging + clone alert system |
| SQL injection | Django ORM parameterized queries |
| XSS | React JSX escaping + Django CSP headers |
| CSRF | DRF CSRF protection + `SameSite` cookies |
| Image upload abuse | 5MB size limit + MIME type validation |
| Brute force | Rate limiting 30 req/min on verify endpoint |
| Insider abuse | Audit log on all admin actions |
| Secrets | Environment variables only — no hardcoded secrets |

Clone evaluation results are written to `evaluation/clone_detection_results.csv` and `.png`; OCR evaluation writes a per-image CSV under `evaluation/`. The chatbot evaluation uses a bilingual set of 60 supported question/answer pairs plus out-of-context refusal cases. Synthetic scans are training/evaluation examples, not evidence that the detector is clinically or operationally validated.

Configure optional hosted chat in `.env` or the hosting provider's private environment settings with `LLM_PROVIDER` (`anthropic` or `openai-compatible`), `LLM_API_KEY`, and `LLM_MODEL`. For a compatible endpoint, set `LLM_BASE_URL`. A hosted provider key is optional: without it, the chat returns the requested section directly from the selected registered medicine record (no external AI-generated answer). Only the user's question and selected medicine context are sent to a configured provider. Never put provider keys in frontend `VITE_` variables or commit them.

### Live Africa's Talking SMS/USSD setup

The application has callback handlers and SMS reply delivery, but the project does not include provider credentials, an approved sender ID/shortcode, or a provisioned USSD service code. These must be obtained from your Africa's Talking account. Do not commit credentials or paste them into source code.

1. In the Africa's Talking dashboard, create/select a **production application**, obtain its username and API key, and request/activate the SMS sender ID or shortcode and USSD service code you need. Production provisioning and account approval are handled by the provider.
2. Deploy the backend behind a stable public **HTTPS** domain. `localhost` and `127.0.0.1` callback URLs cannot be reached by Africa's Talking. A temporary HTTPS tunnel may be used for a supervised test, but it is not a production deployment.
3. Configure the root `.env` file (never commit it):

   ```dotenv
   AFRICASTALKING_ENABLED=True
   AFRICASTALKING_USERNAME=your-production-username
   AFRICASTALKING_API_KEY=your-private-production-api-key
   AFRICASTALKING_BASE_URL=https://api.africastalking.com
   AFRICASTALKING_SENDER_ID=your-approved-sender-id
   AFRICASTALKING_CALLBACK_TOKEN=generate-a-long-random-secret
   ```

   Leave `AFRICASTALKING_SENDER_ID` blank if the provider configuration does not require one. Generate a callback token locally, for example with `python -c "import secrets; print(secrets.token_urlsafe(32))"`. Keep it private.
4. In the provider dashboard, register these callback URLs, replacing the host and token with your own:
   - SMS inbound: `https://your-domain.example/api/v1/gateway/sms/?token=YOUR_CALLBACK_TOKEN`
   - USSD: `https://your-domain.example/api/v1/gateway/ussd/?token=YOUR_CALLBACK_TOKEN`
5. Configure the SMS keyword/shortcode and USSD service code with the provider. Restart/redeploy the backend after changing environment variables. Keep `AFRICASTALKING_ENABLED=False` until the account and callback URLs are ready.

When enabled, incoming SMS verification requests receive an outbound SMS reply, including the `INFO <code>` medicine-information flow. USSD results are returned in the HTTP response expected by the USSD gateway. The callback token is checked before processing. Provider delivery and service charges may apply. Start with a provider-approved test/low-volume setup before inviting customers; the local `/simulator` does not use this live integration.

## 🌍 Deployment (VPS)

### Render + Neon (hosted student/demo deployment)

The backend now uses SQLite for local development and PostgreSQL when `DATABASE_URL` is set. Keep database passwords and all secret keys in Render environment variables; never commit them or paste them into chat. If a database URL has been exposed, rotate its password before deploying.

1. Push this project to its own GitHub repository. Do not include `.env`, SQLite databases, virtual environments, or generated model files.
2. In Neon, create a PostgreSQL project. Copy its connection string and keep it private. Choose a region near the Render backend (Frankfurt is a reasonable choice if selected for both).
3. In Render, create a **Web Service** from the GitHub repository and set its **Root Directory** to `backend`. Choose a Python runtime and, if available, the same region as Neon.
   - Build command: `pip install -r requirements.txt && python manage.py collectstatic --noinput`
   - Start command: `daphne -b 0.0.0.0 -p $PORT mediverify.asgi:application`
4. Add these backend environment variables in Render (use Render's generated backend hostname for the host):
   - `DEBUG=False`
   - `DJANGO_SECRET_KEY` and `HMAC_SECRET_KEY`: separate, randomly generated secrets (at least 50 and 32 characters respectively). Generate values locally with `python -c "import secrets; print(secrets.token_urlsafe(48))"` and `python -c "import secrets; print(secrets.token_urlsafe(40))"`, then enter them directly as private Render environment variables.
   - `DATABASE_URL`: the newly rotated Neon connection string
   - `ALLOWED_HOSTS=YOUR-BACKEND.onrender.com`
   - `CORS_ALLOWED_ORIGINS=https://YOUR-FRONTEND.onrender.com`
   - `CSRF_TRUSTED_ORIGINS=https://YOUR-BACKEND.onrender.com,https://YOUR-FRONTEND.onrender.com`
   - Optional hosted chat: `LLM_PROVIDER`, `LLM_API_KEY`, `LLM_MODEL`, and optionally `LLM_BASE_URL`. Add these only in the backend's private Environment settings. The chat continues to use offline record-based answers when no key is configured.
   - Optional LLM/Tesseract/Africa's Talking variables only when those services are configured. Do not enable live Africa's Talking until its account, sender/service code, and public callbacks are ready.
5. After the backend deploys, create a Render **Static Site** from the same GitHub repository with **Root Directory** `frontend`.
   - Build command: `npm ci && npm run build`
   - Publish directory: `dist`
   - Set `VITE_API_URL=https://YOUR-BACKEND.onrender.com/api/v1` in the Static Site environment.
   - Add a rewrite rule from `/*` to `/index.html` with status `200`, so React client-side routes work on refresh.
6. Once the Static Site is deployed, update the backend's `CORS_ALLOWED_ORIGINS` and `CSRF_TRUSTED_ORIGINS` with its exact HTTPS origin, then redeploy the backend.
7. Seed demonstration data intentionally from the Render Shell/one-off command after deployment: `python manage.py seed_data`. This creates demo users and records; do not make this a repeat-on-every-deploy command. Create the regulator account through a controlled setup path and change demo passwords before exposing the service publicly.
8. Test the hosted frontend, API docs at `https://YOUR-BACKEND.onrender.com/api/docs/`, authentication, and database persistence across backend redeploys. The free Render web service can sleep while idle; Neon Free has usage limits and may scale compute to zero. Check the providers' current terms and keep backups of data you need.

The backend start command uses Daphne (ASGI) for both HTTP and authenticated regulator WebSockets. The default in-memory channel layer is suitable for the single-instance demo service; multiple backend instances require a shared channel layer such as Redis. Run database migrations separately before the server starts, for example from your local machine with the Render environment values and Neon `DATABASE_URL`; do not put migrations in the start command, where they can delay port binding.

This is suitable for a class presentation, not a production medicine-authentication service. A Render + Neon deployment does not connect MediVerify to an official medicine registry or independently authenticate real manufacturers' codes.

```bash
# 1. Clone repo and set .env
cp .env.example .env
# Edit: DJANGO_SECRET_KEY, HMAC_SECRET_KEY, DATABASE_URL, AFRICASTALKING_API_KEY

# 2. Deploy with Docker
docker-compose -f docker-compose.yml up -d --build

# 3. Create admin user
docker exec mediverify_backend python manage.py createsuperuser
```

Minimum VPS: 1 vCPU, 1GB RAM, Ubuntu 22.04 (DigitalOcean/Hetzner ~$6/mo)
